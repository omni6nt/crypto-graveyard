# CRYPTO GRAVEYARD — PROJECT ROADMAP

**Internal target:** December 2, 2026. **Official Kiroween deadline:** December 4, 2026, 2:00 PM Pacific / 11:00 PM Lagos. This is a compressed plan, not a guarantee.

## Operating rules
- User is project owner and approves scope.
- ChatGPT supports planning, research, drafting, implementation, review, and debugging.
- Kiro must be used meaningfully; document only features actually used.
- No unapproved features.
- Keep repository public and root `.kiro/` tracked.
- Project must be newly created within contest period; preserve development evidence and disclose pre-existing materials as required.

## Phase 0 — Repository and Kiro foundation
Deliver: public `omni6nt/crypto-graveyard`; local clone opened in Kiro; root `.kiro/`; README and MIT license; product/visual/technical/research steering; project log. Exit: repo opens, initial commit pushed, `.kiro` tracked, no secrets committed.

## Phase 1 — Specifications
Deliver: master blueprint, MVP requirements, research standard, roadmap, and Kiro specs for shell, cemetery/navigation, case file, examination, progress, references, nomination form, outro. Exit: P0 criteria clear, exclusions recorded, owner approves.

## Phase 2 — Research and case data
Build dossiers for all eight cases, source registers, timelines, warning signs, 6–8 examination items each, legal/current-status verification, and relevant Intuition references. Exit: every published case passes research gate; factual claims and explanations have source IDs. If all eight cannot pass by content freeze, publish only those that do.

## Phase 3 — Individual asset production
Deliver canonical Coroner full-body asset; five separate expressions; cemetery background; gate closed/open; eight tombstone designs or reusable components; separate props/environment elements; UI icons/effects; asset manifest and `assets/CREDITS.md`. Exit: separate files, descriptive names, clean transparency/crops, recorded origin/tool/date/license, no copied franchise art or unauthorized logos/music.

## Phase 4 — Implementation order
1. Semantic HTML shell and responsive layout.
2. Case data model and loader.
3. Directory/navigation.
4. Reusable case-file page.
5. Sources and claim labels.
6. Examination flow.

## Phase 5 — Testing
Test schema/source integrity, all routes, timeline order, examinations/retakes, storage persistence/corruption, entrance skip/return behavior, reduced motion, sound-off, keyboard/focus, mobile from 360px, external links/form, console errors, and broken assets. Exit: P0 acceptance tests pass and critical issues are resolved/documented.

## Phase 6 — Deployment/submission
Deliver public app URL, public GitHub repo, visible license, root `.kiro`, truthful Kiro-use writeup, public YouTube demo under three minutes, Devpost description/screenshots/links, blog/social bonus materials if feasible. Test from logged-out browser.

## Risk register
- Research breadth: reusable template, primary sources, cut cases that fail gate.
- Changing legal status: record cutoff and recheck before release.
- Asset bottleneck: essential assets first; reusable components.
- Scope creep: enforce P0/P1/P2 and require approval.
- Storage failure: fallback and tests.
- Mobile cemetery usability: directory alternative.
- Regional/credit issues: continue setup without assuming credits; document actual Kiro use.
- Deployment: deploy minimal shell early.
- Submission errors: maintain checklist and test all links.
